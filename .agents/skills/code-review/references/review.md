# Review method

- Target = identify the requested artifact + comparison base. Use the supplied PR/base; otherwise resolve the branch's intended target from repository evidence. Upstream tracking alone may identify the same branch, not its merge target. Unclear scope → state the gap before drawing conclusions.
- Diff = read full hunks + affected owners/callers. Branch/PR → cumulative diff against its merge-base; commit → requested patch; working tree → staged + unstaged + in-scope untracked files; pasted diff → the pasted text is the artifact and needs no base. The checkout may hold its files before or after the patch: say which state you read. Include local changes in a branch review only when in scope. Empty diff → no changes to review, not a failed review.
- Intent = compare against the user's request, supplied/linked requirements and the project's `REQ-` rules in `docs/requirements.md`. Check missing behavior, changed contracts + unsupported additions; compatibility code for a shape that never shipped is one. Missing requirements → state that limit; do not infer intent from the implementation itself.
- Claims = trace the failure scenario through actual data, state, permissions, ordering or callers. For plans/diagnoses/proof, separate proposed behavior from implemented behavior and claimed results from observed results.
- Tests = apply [Test design + quality](../../he/references/testing.md) to affected tests and claimed proof. Passing gates do not establish requirement coverage, realistic UI behavior or deployed success. Removed test, row or assert that the plan says another test covers → break the code it guarded; that other test must fail, else finding.
- Hot paths = no [HE-HOT-PATH](../../he/references/requirements.md#he-hot-path) finding was hidden by code that still does the same work; apply [Hot paths + data layout](../../he/references/efficiency.md#hot-paths--data-layout) to changed loops, queries and handlers.
- Unattended sends = [HE-SEND-LIMIT](../../he/references/requirements.md#he-send-limit): change to a timed job, queue worker, webhook handler, alarm or background retry, or to what starts it → follow the failure path to each send, untouched senders included; no limit that holds when each run fails, or an alarm that sends for each failed run → finding. Change to code that sends, to seed, test or staging data that holds recipients, or to the config that picks the provider account → a real send from test or staging data (not capture or sandbox mode) through an account that a production app uses, or to a real person who is not a named test recipient → finding.
- Screen text = [HE-NO-TEXT-WALLS](../../he/references/requirements.md#he-no-text-walls): a date, time, name, amount or count inside a sentence is a finding; server-built screen text with no test through `text-walls --stdin` is a finding.
- Skill text = changed skill or reference prose → the plan or PR records a [Writing Great Skills](../../writing-great-skills/SKILL.md) Reader check on it, and each sentence the Reader quoted was reworded or moved; no record → finding.
- Visible change = make a new checkout of the PR head for this review, for example with `git worktree add`. Never use the author's checkout. In it, start a browser and capture the After screens. Then run `python3 .hooks/hard-eng.py look <after images>` on your own captures. For a screen that a browser does not serve, download the After attachments from the PR body into that checkout, then run `look` on those files. In a read-only challenge, or when you cannot make a checkout, run no `look`, `browser capture` or `browser measure`, and skip every step here that needs them. For a web screen, also run neither when you cannot start a browser. List the missing `look` run as a coverage limit. Then judge only the `Look review:` block in the PR body. Do not accept a typed Pass line in place of a `look` block. Put the `Look review:` block from your own `look` run in your review result, not in the PR body. It holds one line per [Usability](../../he-plan/references/ux.md) rule, for all screenshots together. Judge a rule that an image cannot show from its test or code. A Fail is a finding. A missing after screenshot is a finding. A PR whose `ux_reference` is the `N/A — unchanged:` line has local links that do not open in your checkout. That is not a missing after screenshot. For a PR whose `ux_reference` is the `N/A — unchanged:` line, capture Before at the merge base and After at the PR head, with `browser capture --name before` and `--name after`. A byte difference at any width is a finding. In the PR body, a missing `Look review:` block, or one with a rule line marked Fail, is a finding. In that checkout, run `browser capture` or `browser measure` at the PR head. A screen that a browser does not serve needs none. A finding in the `.hard-eng/browser/<name>-<width>.json` record that your own run writes is a finding. When your own `look` run prints no block, or the block's `- verdict:` line is not `clean`, that is a finding.
- Finding = precise location + code/evidence fact + triggering condition + concrete impact + smallest useful correction. Rank by impact and likelihood. Remove preference-only, duplicate, speculative and already-disproved candidates; an unresolved question is not a confirmed defect.
- Plan match = when the task has a PLAN.md, list every acceptance item as met or not met with its test/check result as proof; skip none. No plan → say so.
- Result = actionable findings first, then the Plan match, then material coverage limits + unverified checks. No findings → say so without implying unperformed verification or approval of unknown behavior.
