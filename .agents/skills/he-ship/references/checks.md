# Native shipping checks

Load for configuring or running HE Ship. The initial verifier supports GitHub PRs whose head and base belong to `origin`; fork PRs and other providers are unsupported. Missing `gh`, authentication or configuration is a blocker. The checks use real Git/`gh` responses and trusted project commands. Fixture responses are only test evidence, not hosted delivery proof.

## Publication privacy

- Audience = establish the destination and who can read it before recording tracked content or publishing. General merge/publish authorization does not authorize disclosure of private context.
- Public shared tooling = use public repository facts or accurately labeled synthetic reproductions. Exclude private consumer/client identifiers, personal data, private task/commit IDs, internal URLs, local paths and private operational logs/screenshots. Keep real private evidence within its authorized audience; do not relabel it as synthetic.
- Review = inspect the complete payload: diff, plans/decisions/fixtures, filenames, branch/commit text, PR titles/bodies/comments, links, logs and attachments. Sanitize descriptions and evidence before publication. A passing secret scan cannot establish privacy.
- Disclosure = stop further exposure, sanitize current text within existing authority and report remaining history/copies. Current-text cleanup does not erase Git/edit history, notifications or copies; history rewriting requires separate authorization.

## Project contract

Add `shipping` to the existing `hard-eng.gates.json` from observed repository requirements:

```json
{
  "shipping": {
    "base": "main",
    "checks": ["hard-eng"],
    "ui_paths": ["web/**"],
    "ci_seconds": 180,
    "pre_push_seconds": 180,
    "delivery": []
  }
}
```

Values above are an example, not universal defaults. Use the actual target, required check names, UI owners and measured budgets. `ci_seconds` measures each named check, not upstream work hidden behind an aggregate; follow [CI ownership](../../he/references/gates.md) when consolidating existing jobs. A required check must conclude `success` on every PR; `skipped` proves nothing and is rejected. Put a path condition on the job's steps, never on the job, and add one step that reports nothing to verify, so a docs-only PR still concludes the check. An empty UI path list explicitly describes a nonvisual project. Missing/invalid policy blocks pushes, Complete plans selecting delivery and ship checks. Pre-push reads the shipping policy of the pushed commit, rejects direct updates to its base and verifies that commit; a full `check --base <ref>` (not `--quick`, `--plan-stage Draft` or `Ready`, a language filter, `--without-dependents`, `--related-tests` or in CI) that passed on a clean tree stands in for the push check only when the push has the same commit and the same base commit as that check (the base of a push = the branch point on a first push or after a rewrite, the old remote tip on a later one), in the same worktree, within 30 minutes of the start of that check; with mutation on, a quick check still runs before the mutation report. `pre_push_seconds` bounds each local gate; a gate with a recorded pass also stops at 3× that time (at least 600 s), so a hung check fails early. A whole run over the budget only warns, because rejecting a passed push discards the proof. The optional `pre_push_mutation_seconds` (default 120, 0 skips) caps the report-only mutation run after the checks pass; it is not part of `pre_push_seconds`. Run the full report with `python3 .hooks/hard-eng.py mutation --base <ref>`. The budget never permits omitting checks. Push to GitHub over HTTPS: an SSH connection can drop while the hook runs, failing the push (exit 141) after checks pass.

Optional `shipping.pre_push_checks`: `"local"` (default) runs the full check before each push. `"ci"` leaves the full check to CI. With `"ci"`, pre-push still refuses a push straight to the base branch. It still warns when origin uses SSH, and it still scans the pushed commits for secrets. With `"ci"` and `pre_push_mutation_seconds` above 0, pre-push then runs two more steps: a quick check that installs dependencies, and the mutation report. The `"ci"` value takes effect only when `hard-eng.gates.json` on the remote base branch also says `"ci"`; the pushed commit cannot switch it on for itself. A `"ci"` policy makes `check` and pre-push fail with an error unless both of these hold. First, the project has the `secrets-history` gate and `scan_git_history` is on. Second, a workflow runs `hard-eng.py check` on every pull request. In that workflow, an `if:` of only `${{ !cancelled() }}` is allowed. A `branches` list that holds `'**'` and has no `!` entry is also allowed. The job that runs the check must have no `if:`, and no job listed in its `needs:` may have one. The step that runs the check must have no `if:`. The one exception to the step rule is a pair of steps that run the check with the conditions `X == 'true'` and `X != 'true'`, where X is one dotted name such as `steps.impact.outputs.docs_only`; the installed workflow does this. The job rule still applies. The command may use only `--base`, `--shard` and `--plan-stage Complete`. A commented-out command does not count. CI must run the whole check as the last line of a `run` step, so the step passes or fails with the check. These do not count: the check inside a shell `if`, `case` or loop; the check text only printed by `echo`; the check on a line that also has `||`, `|`, `;`, `!` or a single `&`, before or after the check; the check in a `run` block that holds an `exit` or `return` above it with no number above zero right after it, such as `cond && exit 0`, a bare `exit`, `exit "$CODE"`, an `exit 0` inside a function, or `trap 'exit 0' EXIT`, because the judge cannot tell when that command runs; the check followed by any later line or command, except `&&` and one more command on the same line, with nothing after it; and a check in a step or job that has `continue-on-error: true`. Each of these lets CI pass when the check fails. When a package gate has `shards`, the workflow needs a job that runs `check --shard rest` and a job that runs `check --shard merge`, and neither job may have an `if`. A workflow with `check --shard rest` alone skips the sharded tests. The merge step fails when a numbered shard, such as `check --shard 1`, sent no report, so the judge needs no rule for the numbered shards. A workflow whose only trigger is `workflow_call` counts when a `pull_request` workflow calls it from a job that has no `if:` and whose `needs:` jobs have none. Any other `pull_request` trigger with a `branches`, `branches-ignore`, `paths`, `paths-ignore` or `types` filter is refused. When `check` runs in CI without `--quick` and the base policy says `"ci"`, it fails if a gate, such as a formatter, changed a tracked file. Hard Eng does not enforce that CI must pass before merge. Branch protection cannot be read offline, so Hard Eng does not check it. Before adding the key, install a Hard Eng release that lists `pre_push_checks`. Older releases refuse unknown shipping keys.

A big change (the size rule in `check`'s "Size" line) also needs `python3 .hooks/hard-eng.py challenge` run on the current HEAD before `ship` ready or merge: the other agent reviews it read-only ([challenge](../../code-review/references/challenge.md)). A missing record blocks; a `not done` record passes, and the PR evidence states "independent review not done: <reason>". Small changes skip it.

Installed-scaffold freshness is checked without mutation at `ship` ready and merge; a newer CI-verified revision or unavailable freshness evidence blocks that stage. The end of a reply makes no update-freshness request: it adds a note from the session-start update result (still running, failed or unknown) and never blocks on freshness. The block names the next step: no open update PR → `python3 .hooks/hard-eng.py update-pr` (pushes `hard-eng/update`, opens the "Update Hard Eng" PR and merges it only after all checks on its head pass, no approval; merge denied → rerun with `--no-merge` and give the user the merge command it prints once checks pass); failing → fix it first on that branch in its own worktree; pending → wait for the checks, then rerun `update-pr` to merge it; merged → rebase the task branch on the base branch. This update PR is allowed beside the task's main PR, whatever one-PR habit applies. Reverify affected work afterwards; never advance the revision marker manually. Source development without an installed marker is outside this update check.

For deployment, `delivery` contains existing project verifiers: `{"name":"production","command":["python3","scripts/verify_deployment.py"]}`. Reuse a native project command before adding a script. Each receives `HE_SHIP_REVISION` and `HE_SHIP_PR_URL`; it must inspect the actual deployed state and emit JSON `{"status":"passed","revision":"<observed source revision>"}`. Nonzero exit, missing/wrong revision or absent required commands fail. A script that echoes the expected environment variable proves nothing; validate an old-version failure and current-version success at the deployed boundary. Once `delivery` lists a check, plans use `Delivery target: Deploy` (`Merge` fails the plan check), and a small change without a plan runs the delivery checks too.

Keep one declaration in the existing plan's Verification section:

```text
Delivery target: Deploy
Delivery: Pending — production verification and cleanup remain required.
```

Allowed targets: `PR`, `Merge`, `Deploy`. Local build acceptance stays in the existing checklist; full remote requirements stay explicitly pending until proven. No new plan Status values or unchecked future-delivery checkbox that prevents the necessary pre-push Complete gate.

## UI evidence in the PR

For changes matching `ui_paths`, compare the actual baseline and final appearance at the same route, state and viewport. Publish a before/after pair only when appearance differs, using distinct, inspected GitHub attachments. Use one pair per route, state or viewport that changed. The verifier needs at least one pair, equal counts of `Before:` and `After:`, and no repeated URL:

```markdown
Before: ![Before](https://github.com/user-attachments/assets/actual-before-id)
After: ![After](https://github.com/user-attachments/assets/actual-after-id)
```

When the installed `gh pr create` or `gh pr edit` supports `--attach`, upload
images or videos directly; a browser upload is not a prerequisite. Put each
label on its own line, then the local Markdown reference as the only content in
its paragraph in the body file. Use `.png` or `.mp4` paths alike:

```markdown
Before:

![](evidence/before.mp4)

After:

![](evidence/after.mp4)
```

Create or update the PR with that body and both local files:

```sh
gh pr create --title "Title" --body-file pr-body.md \
  --attach evidence/before.mp4 --attach evidence/after.mp4
gh pr edit https://github.com/owner/repo/pull/123 --body-file pr-body.md \
  --attach evidence/before.mp4 --attach evidence/after.mp4
```

GitHub CLI rewrites each local reference to a GitHub asset URL under the same
label: a raw URL for a video, `![name](url)` for an image. The verifier accepts
either only under `Before:` or `After:`, and mixed image/video pairs work. An
`--attach` file that the body does not reference is appended as an unlabelled
image at the end of the body; it does not count.

When appearance is unchanged, omit the duplicate attachments and record one comparison note instead:

```text
UI appearance: unchanged — inspected the baseline and final dashboard at the same state and viewport; no visible difference.
```

Describe the actual comparison, not an assumed result. Missing proof is not unchanged appearance. Apart from the two links in its own `N/A — unchanged:` line, a labeled Before/After attachment cannot accompany this declaration. The `UI appearance: unchanged` note does not waive behavior tests. Distinct URLs alone do not establish a visible difference. For different file bytes, see the `N/A — unchanged:` rule below.

A `ui_paths` change that Hard Eng counts as visible is a visible change, even when it changes nothing on screen. That means markup, styles, assets, theme, text catalogs, or code that writes to the page. For such a change, the free `N/A — reason` that the plan template allows for nonvisual work is refused. On a visible change, `ship --stage ready` also needs the items below. When the appearance is unchanged, `ship` checks only the equal captures, so run `look` on them yourself. CI cannot download a private attachment. So the CI `pr text` check tests only the form of the `Look review:` block and of the `ux_reference` N/A line:

- For a web screen (a page that a browser serves), each After image comes from `browser capture` or `browser measure`. It is taken at the PR head from a clean tree. It shows the page that the plan's `Surface:` route names (a plan with the `N/A — unchanged:` line needs no route). For a web screen with After images, put the route right after the surface kind in every `Surface:` form, starting with `/` (`Surface: Existing — /settings, rendered by ...`). The page path of each After image starts with that route. Its record (`.hard-eng/browser/<name>-<width>.json`) has no finding at each standard width. Measure a state reached by clicks with `browser measure` in its open session. Draw rings only with `--ring` (on `browser capture` or `browser measure`). On a web change, `ship` refuses a ring drawn on the image afterwards, because it changes the hash. `ship` skips this bullet only when every changed screen file ends in `.dart` or `.swift`. Such a screen may draw its ring on the image. It still needs the `look` record below. For a Flutter app with a web build, take the browser capture yourself anyway.
- `python3 .hooks/hard-eng.py look <image>...` opens each image with the other agent. It uses a fresh session of the same agent when the other CLI is missing. It saves its record. When the result is clean, it prints a folded `Look review:` block. The block holds these lines: one per Usability rule, one `- image:` hash line per After image, a `- verdict:` line, and a last `- record: <hash>` line. Copy the block into the PR body unchanged. Run `look` after the last commit, because a later commit makes `ship` refuse the record. `ship` refuses a missing record or one whose result is not `clean`.
- `ux_reference` may be N/A on a visible change only in this form: `N/A — unchanged: ![Before](..) ![After](..) — <screen and state>`. The captures need equal bytes at every width. If the bytes differ at any width, you cannot use this line or the `UI appearance: unchanged` note. Publish a Before/After pair instead, even when you see no difference. This overrides "only when appearance differs" above, and the "unchanged → comparison note" step in [HE Ship](../SKILL.md). Draw no ring. This line is for a web screen only. A screen that no browser serves cannot use it, and publishes a Before/After pair instead. Take both captures in the checkout that runs `ship`, from a clean tree. Check out the merge base and run `browser capture --name before`. Then check out the PR head and run `browser capture --name after`. Each link is the local path of a capture in `.hard-eng/browser/`, such as `.hard-eng/browser/before-<width>.png` and `.hard-eng/browser/after-<width>.png`, in both the plan and the PR body. Do not upload these images. Link one width of each. The check opens the files at those paths and finds the other two widths by the same names. Make that line the whole body of the plan's `ux_reference` section. Copy the same line into the PR body. The `UI appearance: unchanged` note needs a plan with that line. So a PR with no plan cannot use the note on a visible change. It publishes a Before/After pair instead, even when the appearance is unchanged.
- A Flutter screen change needs a widget test that calls the four `meetsGuideline` matchers: `textContrastGuideline`, `labeledTapTargetGuideline`, `iOSTapTargetGuideline` and `androidTapTargetGuideline`.

The verifier checks the declaration or attachment availability/media type; E2E owns inspection of the actual comparison and behavior. Keep baseline/final context in the PR; do not upload sensitive content or fabricate a missing baseline.

## PR text

- Form = a reader with one minute gets the point. Order: a `Summary` of ≤5 bullets (what changes for the user) → one line per main change (list or table) → `Before and after` → proof → limits. Headings + bold lead words. Plain simplified English for people, in the style of ASD-STE100: one idea per sentence, ≤20 words, ≤4 sentences per paragraph. Detail that few readers need (each commit, each review run, timing tables, long proof) → a `<details>` block or a link to the plan. `ready` and CI's `pr text` refuse a wall of text: more than 6,000 visible characters, or a visible line over 600. Fenced code blocks, `<details>` blocks, HTML comments and link targets are not visible text.
- `Before and after` part = for each main change one Mermaid diagram of the old flow + one of the new flow; a main change with no old flow shows two or more diagrams of its new flows. Label each diagram with a bold word, such as `**Before**` or `**After**`. Do not start a line with `Before:` or `After:`. The checker reads such a line as a UI evidence label. It refuses a PR that has one of these lines and also the "UI appearance: unchanged" note. Use quoted labels, no backticks inside labels. Each flowchart node and edge label line has 13 characters or fewer. Count each line on its own; a `<br>` starts a new line. Split a longer label with `<br>`. A node with no label shows its ID, so the ID counts too. GitHub cuts longer lines at zoom levels other than 100%. Use `flowchart TD`, or `LR` with 4 or fewer nodes in a row. `ready` and CI's `pr text` refuse fewer than two Mermaid blocks or a longer label line ([what `ready` verifies](#commands--proof-boundaries)).
- A line that starts `Not checked:`, with the answer on that line (a `- ` or `* ` list mark may come first) = what no check covered, such as a platform, device, deploy or installed project; `Not checked: None — <reason>` when nothing.
- UI change whose appearance differs = before and after screenshots ([UI evidence](#ui-evidence-in-the-pr)) with a red ring on each changed thing: on a web change, draw the ring in the page before the screenshot, only with `--ring` on [`browser capture`](../../e2e/references/browser.md#capture) or `browser measure`. `ship` refuses a ring drawn on the image afterwards. A screen that no browser serves may draw its ring on the image. When stills cannot show the flow, add a video of the whole flow below the pairs, with no `Before:` or `After:` label (the checker needs equal counts of those lines and ignores unlabeled media).
- CI's `pr text` check skips three kinds of PR: the Hard Eng update PR (it keeps its generated text and needs no `Not checked:` line in CI), a PR that the account `dependabot[bot]` or `renovate[bot]` opened (a bot writes its text) and a PR whose base is not the shipping base. It checks every other PR on each push or edit, and applies the [UI evidence](#ui-evidence-in-the-pr) form when the PR changes a `ui_paths` file. Setup installs it beside any GitHub workflow of the project. Run `python3 .hooks/hard-eng.py pr-text --pr <URL or number>` after a PR opens and after each edit; it runs the same rules on the live PR text, and `ship --stage ready` runs them too.

## Commands + proof boundaries

From the task checkout, with its actual PR URL and plan (a change `check` reports as `Size: small` ships without a plan: omit `--plan`; delivery scope is Merge and every check still runs, while a big change without a plan is refused):

```sh
python3 .hooks/hard-eng.py ship --plan PLAN.md --pr https://github.com/owner/repo/pull/123 --stage ready
```

`ready` verifies current PR identity, branch/build evidence, required checks, applicable UI evidence, a PR body line that starts `Undo:` and lists the undo steps on that line, two or more Mermaid blocks in the body (the [PR text](#pr-text) `Before and after` part), a `Not checked:` line, and the two size limits of the PR text form. It also refuses a PR head that is behind its base. Two PRs that pass alone could otherwise break the base together. To recover, rebase on the base, push and wait for the checks again. It also refuses a PR above the HE-PR-COMMITS cap. It also refuses a PR that GitHub cannot rebase, unless the repository forbids rebase merges and allows another method. One cause is a repository setting that allows no other method. Another is a stale GitHub report. When the branch is not behind its base and has no merge commit, closing and reopening the PR can clear it. Each refusal names its fix. It prints a warning when the base branch may not require the checks. A queued check on a self-hosted runner that no runner takes shows after `ci_seconds`, with its runner labels. GitHub fails it after 24 hours. Rerun `ready` once after `ci_seconds` instead of watching. It changes nothing on GitHub. `ready` saves a passed record inside this checkout's Git folder, at `git rev-parse --git-path hard-eng/ship/<PR number>.json`. A typed `gh pr merge` must run in the checkout that holds the record. `merge` runs the same gate. `merge` repeats the `ready` checks, writes a new record, and merges that head with that method. The method is rebase by default. It is a merge commit for a release PR. A release PR has the shipping base branch as its head and another branch as its base. Take a PR that is not a release PR, in a repository that forbids rebase merges. Its method is squash if the repository allows squash, and a merge commit otherwise. A release PR always uses a merge commit. The Claude Bash hook (`.hooks/polling.py`) refuses a command that has the whole word `gh` and the whole word `merge`, with quotes removed. Of those commands, one form passes. It is a plain `gh pr merge <PR>` with a passed record, `--match-head-commit <that head>` and only the recorded method flag, and the method is squash or a merge commit. The hook refuses a typed rebase merge, because a record cannot show that the base has not moved since `ready`. Run `python3 .hooks/hard-eng.py ship --stage merge --merge-method rebase --pr <PR URL> --plan <plan file>` instead of a typed rebase merge. The `ship` command checks that the head holds the newest base commit right before it merges. The hook refuses `--admin` and `--auto` in any typed command. Read commands such as `gh pr view --json mergeStateStatus` pass. The hook does not catch four things. One is a script file or stdin text that holds the merge (`bash merge.sh`, `cat f | bash`, `sh -c "$(cat f)"`). One is a `curl` call. One is a program that calls the API. One is a merge in the GitHub web page. The Codex rule file `.codex/rules/hard-eng.rules` works in trusted projects only. It refuses `gh pr merge`, also behind `env`, `command`, `xargs`, `exec` or `gh` at `/opt/homebrew/bin`, `/usr/local/bin` or `/usr/bin`. It does not catch `-R` or `--repo` before `pr`, or `bash -c` strings. It does not cover `gh api`. Run `merge` only with existing merge authorization. A queued or pending merge is unfinished. Sometimes the only block is a required review that nobody but the author can give. Then `ship --stage merge` merges with `--admin` and reports the bypass. This needs a sole push collaborator with admin bypass. It also needs the newest run of every head check successful, and no change requests or conflicts. Never run `gh pr merge --admin` directly; the hook refuses it.

`delivered` requires actual merge/remote proof and, for Deploy, the configured runtime verification. Before cleanup, retain evidence and make sure no other task uses the checkout. Deliberately remove only known generated build/test artifacts; unknown ignored files are retained. Run `cleanup` from the repository's persistent checkout with `--worktree` naming the completed linked worktree. Native guards must pass; the main checkout, the base branch, a task branch another worktree uses, and a changed/dirty/untracked/locked/current checkout or active Git index lock are retained. Cleanup does not manufacture delivery proof. Use `python3 -B` for the cleanup invocation so Python does not create new bytecode artifacts.

Cleanup requires the captured origin URL to remain the fetch and sole push endpoint. Multiple or differing push URLs and initialized submodules are retained for a repository-owned cleanup procedure; the generic command never force-removes them. Dirty submodule checks override Git's ignore settings.

Record returned results at the same relative plan path in the persistent checkout, recovering the plan from the verified merged revision before removal if needed. Preserve unrelated edits there. Source changes invalidate affected build proof; external outages do not erase valid local checks. Remote branch protection remains project-owned: a repository admin requires the checks at the repository's Settings, Rules, Rulesets, New branch ruleset (Require status checks to pass). This implementation does not change server rules or claim to control unrelated clients.
