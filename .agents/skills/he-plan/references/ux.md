# Repository-grounded UX reference

Apply to visible changes; preview only the flow and states needed for the decision.

- Grounding = inspect the actual website/screen, affected flow and token/theme/component owners in `DESIGN.md` + production code. A dashboard shell alone cannot support decisions about unseen workflows. Missing relevant context → expose the gap; never invent a baseline. A requested change that conflicts with an existing app rule (a rule in `PRODUCT.md`, `DESIGN.md` or `docs/requirements.md`, or behaviour that the code enforces) → find the rule + its reason first; say so before agreeing.
- Usability = judge every proposal, mockup, review and after screenshot against each rule. A Fail means fix the design and inspect it again, before it is shown to anyone. A Pass line you type is a claim, not proof. `ship` refuses an After image with no finding-free record from `browser capture` or `browser measure`. `ship` skips this only when every changed screen file ends in `.dart` or `.swift`. For a Flutter app with a web build, take the browser capture yourself anyway. Judge against these rules:
  - Mistake-proof: risky choices blocked, right answer prefilled; ask "how could a rushed person get this wrong?".
  - Least effort (count: clicks): the app acts when sure and shows a person only what needs them, with a prefilled suggestion. Count the clicks per journey; remove any that are not essential.
  - Observe: never ask a person to record or confirm what the system can already see (messages, replies, logs, payments). Record it automatically and offer undo.
  - Undo: one-tap Undo instead of "Are you sure?"; delete, cancel, refund, access removal and reversing money always ask twice.
  - No clutter (count: kept, removed): the screen asks a person to think and remember as little as possible. For every element ask "would the user miss it?" If not, remove it. No helper sentences, history notes, badges or repeated text buttons where an icon with a screen-reader label or colour says the same. Details one tap away. Count the elements kept and removed. On the web, `browser capture` and `browser measure` report these clutter faults, among others. The first is more than 1 secondary line (text smaller or fainter than the body text) under one heading. The second is a secondary line over 20 words. The third is a password or search field that breaks its row in the Standard patterns table below. Screen text: [HE-NO-TEXT-WALLS](../../he/references/requirements.md#he-no-text-walls).
  - Hierarchy: the one action that matters is the strongest element. Everything else is quieter. One focus per screen. Labels have one meaning. Use one filled button in each group of buttons that sit together, and make the rest outlined or plain. Use at most 2 accent colours in one block (a card, panel or form section).
  - Alignment: one shared left edge for the text and controls of a block. Centred text only for a short single line. Controls sit next to their text, not pushed to the far side of a wide row.
  - Spacing: one spacing scale. More room between groups than inside one. Related things sit close and unrelated things apart. No element touches the edge of its block.
  - Design system: every colour, size, radius and component comes from the project's tokens and components, in `DESIGN.md` and the code. A one-off size or radius needs a reason in the plan. A new colour goes in a theme or token file ([HE-UI-SOURCE](../../he/references/requirements.md#he-ui-source)).
  - Messages: say what happened and what to do next. Use plain, calm and positive words, without blame, in the `PRODUCT.md` tone. A confused user means the screen changes, not the user.
  - States: empty and first-use screens say what to do next; loading never shows 0 or stale numbers; a slow or failed connection keeps typed input and says so; one press saves once; an automatic job that stops, pauses or falls behind tells a person at once, with what to do.
  - Time: times show in the user's local time; time logic gets time-zone and clock-change tests.
  - Audit: in an app with staff or admin roles, each of their actions writes an audit row (who, when, what).
  - Accessibility: touch targets at least 44 × 44 pt on iOS, 48 × 48 dp on Android and 44 × 44 px on the web. A web link that shows at 390 or 768 px is a link that people tap, and needs 44 × 44 px. Only a link that shows at 1280 px alone may be 24 × 24 px (WCAG 2.5.8). On the web, the measure flags a button or form control under 44 px and a link under 24 px. Make buttons and form controls 44 × 44 px. The measure checks links only against 24 px, so check the 44 px size yourself. Larger for main controls. Text at least 11 pt on iOS, 11 sp on Android and 11 px on the web. Contrast at least WCAG AA: 4.5 to 1 for normal text and 3 to 1 for large text. Screen-reader labels.
  - Widths: check each width the app supports. For the web, check phone 390, tablet 768 and desktop 1280 px.
  - Performance: name the screen's data reads, payload size and what loads lazily, per [efficiency](../../he/references/efficiency.md).
- Look review = When the result is clean, `look` prints a `Look review:` block for the After images. It holds one line per rule, one `- image:` hash line per After image, a `- verdict:` line and a last `- record:` line. Copy that block into the PR body unchanged. Do not paste the block of a mockup.
- Standard patterns = each row states behaviour and placement only. Use the project's `DESIGN.md` and tokens. With none, use the design the user asked for, else one the agent picks. A plan that changes a control follows its row. A plan that differs from a row writes why in the plan. On the web, a row that the measure checks (Password field, Search field, Button group, Secondary text) cannot differ, because `ship` refuses any finding. The user approves each difference from any other row in the `Handoff: Approval` step ([he-plan](../SKILL.md)) before build. In Autonomous mode, the task's own authorization stands for that approval:

| Control            | Standard form                                                                                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Password field     | A reveal control inside the field: an icon with a screen-reader label. The control shows no text, and no text button sits beside the field. The field keeps its visible label. |
| Search field       | A search icon inside the field and the project's shared search component (if none exists, see Any control). No separate text button beside it.                                 |
| Form field         | A visible label for each field, not a placeholder alone.                                                                                                                       |
| Destructive action | Asks twice before it acts. Destructive actions are delete, cancel, refund, access removal and reversing money.                                                                 |
| Other action       | One tap, then one-tap Undo.                                                                                                                                                    |
| Empty screen       | One line that says the next step, plus the action.                                                                                                                             |
| Error              | What happened and what to do, in plain words, next to the thing that failed.                                                                                                   |
| Button group       | One filled button in each group of buttons that sit together. The other buttons are visibly quieter.                                                                           |
| Secondary text     | At most 1 line under a heading or card, at most 20 words.                                                                                                                      |
| Any control        | Reuse the project's shared component. If none exists, add one new shared component with a mockup. Name it in `Controls:` before any code (see Record).                         |

- Brief = a brief that asks a subagent for a design, mockup or preview links this file, includes the full Usability list and states the job, the users and the constraints. It never dictates the layout, the elements per row or the buttons. Process steps that the requester describes are inputs to automate, not screen elements.
- Pick the first surface below that fits ([HE-REAL-APP-PREVIEW](../../he/references/requirements.md#he-real-app-preview)). Planning may build the proposal in an isolated checkout; production implementation still waits for Ready + authorization. No mandatory video or extra visual-testing platform.

| Surface                                           | Preview + baseline                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Existing — <actual route/screen + source owner>` | Required when the screen exists. Capture the unmodified app and render the proposal through that screen in an isolated checkout. Preserve its UI tree; assert route/state before capture. A reconstructed page is a Mock, not an actual-app capture.                                                                                 |
| `New — <new screen + source owner>`               | A new screen in an app that runs: render it in the app with repository components/tokens; the nearest existing flow is the baseline. Only an app with no prior UI may use `Before: N/A — <reason>`; label assumptions from the brief/assets.                                                                                         |
| `Mock — <actual design-system/component owners>`  | Only when the app cannot be built or rendered locally. Embed the change into the existing website reference, or make a lightweight HTML/image mock using its real design system; show decision-bearing states and label it a mock. Link an inspected baseline when available; otherwise `Before: N/A — <why the app cannot render>`. |
- Render + inspect = use existing browser/device tools; use [E2E](../../e2e/SKILL.md) for runtime visual inspection. For bitmap concepts/assets, use the available imagegen skill; HTML/CSS or existing vectors are sufficient otherwise. Inspect the rendered proposal at affected sizes/states and show it in the conversation. A path, unopened image or explanatory panel is not a shown workflow. Reuse inspected evidence while it still matches the proposal.
- Record = `Result` + `Evidence`, then `Surface`, `Before`, `Proposed`, `Controls`, `Capture`, `Review`, `Rules` in the existing plan. Take a web screen whose PR will carry After images. In `Surface:`, put the route right after the surface kind, from the first plan draft. The route starts with `/` (`Surface: Existing — /settings, rendered by ...`). `Controls:` is one line. Split its entries with `; `. Each entry takes the `reuses` or the `new` form in the block below. `None — <reason>` stands alone as the whole line. The mockup image in a `new` entry is a file committed in the repository. Other preview files, the `Proposed:` image included, stay in ignored storage. The user approves each `new` entry's mockup in the `Handoff: Approval` step. In Autonomous mode, the task's own authorization stands for that approval. The plan check is `python3 .hooks/hard-eng.py check --plan-stage Ready`. It refuses a `ux_reference` section that has no `Controls:` line. A section whose whole body is an N/A line needs no `Controls:` line. A plan that makes a visible change in a `ui_paths` file of a web screen but changes nothing on screen keeps its normal proposal at Ready. After the last code commit, replace the `ux_reference` body with the `N/A — unchanged:` line ([checks](../../he-ship/references/checks.md#ui-evidence-in-the-pr)) and commit that plan change. Then, from a clean tree, capture Before at the merge base and After at that new head, as [checks](../../he-ship/references/checks.md#ui-evidence-in-the-pr) says. Run `look` on the After captures. If the Before and After bytes differ at any width, put the normal proposal back, commit it, and publish a Before/After pair. No other N/A form is accepted for such a plan. A screen that no browser serves keeps its proposal and publishes a Before/After pair in the PR. It refuses a reused path that is not under `ui_paths`. It refuses a `new` entry whose mockup is missing, is not a repository file or has no `look` record. `ship` also refuses a reused path that git does not track. The checks cannot prove that the user approved the mockup. The `look` record check runs only locally. A `look` record is a file in the folder `git rev-parse --git-path hard-eng/look` of the checkout that ran `look`. There is one for each commit and set of images. A run on other images does not replace it. A later commit does not void a mockup's record, because the plan check finds it by the image hash. A linked worktree has its own folder. Run `look` on the mockup in the checkout that runs the plan check. Proposed is a Markdown image. Capture names the actual rendering/capture method + observed result; Review names the inspected states/devices, comparison and direction. Rules = one `- ` line per Usability rule, below the `Rules:` line: `- <rule>: Pass|Fail|N/A — <text>`. `<rule>` is the rule's name without its marker. Pass or Fail text says what was checked on the inspected image. For a rule that an image cannot show (for example Time, Audit, Performance), it names the test or the code. N/A text gives the reason why the rule does not apply. A count rule's Pass puts a number directly before each unit word of its marker (`2 clicks`; `7 kept, 3 removed`). Any Fail → fix the design + inspect it again + judge again before it is shown. `Result: Passed` means the preview was rendered, inspected and shown; it does not record user approval. Before an approval handoff the direction may await the user's decision; Ready requires that decision settled within the task mode.

  ```
  <control> — reuses `<repo path>`
  <control> — new `<repo path>` — mockup ![alt](<repo path of the image>)
  None — <reason>
  ```

- Keep preview source isolated and artifacts in existing ignored/output storage. Link them without new receipts/hashes. Tracked non-Markdown files remain implementation inputs to the completion gate. Nonvisual work uses a concrete N/A reason; unavailable required proof remains blocked.
- User changes direction → update, inspect and show the matching mock/capture. For build verification, compare the actual app with the accepted reference and run the affected journey. A mock does not establish production fidelity or runtime success; recover the real before capture before implementation for PR evidence.

The gate validates declared fields. It does not validate image authenticity, design quality or whether the agent showed the proposal. `ship` also checks the `browser capture` or `browser measure` record and the `look` record of each After image. Image authenticity and design quality need inspection, and a Passed label cannot replace them.
