# Repository-grounded UX reference

Apply to visible changes; preview only the flow and states needed for the decision.

- Grounding = inspect the actual website/screen, affected flow and token/theme/component owners in `DESIGN.md` + production code. A dashboard shell alone cannot support decisions about unseen workflows. Missing relevant context → expose the gap; never invent a baseline.
- Usability = judge every proposal, mockup and review against these; send back a design that fails one:
  - Mistake-proof: risky choices blocked, right answer prefilled; ask "how could a rushed person get this wrong?".
  - Least effort: the app acts when sure and shows a person only what needs them, with a prefilled suggestion. Count the clicks per journey; remove any that are not essential.
  - One-tap Undo instead of "Are you sure?"; delete, cancel, refund, access removal and reversing money always ask twice.
  - Calm screens: one focus, clear hierarchy, few elements and colours, labels with one meaning, no unneeded subtitles.
  - Messages say what happened and what to do next, in plain words, without blame, in the `PRODUCT.md` tone. A confused user means the screen changes, not the user.
  - States: empty and first-use screens say what to do next; loading never shows 0 or stale numbers; a slow or failed connection keeps typed input and says so; one press saves once; an automatic job that stops, pauses or falls behind tells a person at once, with what to do.
  - Times show in the user's local time; time logic gets time-zone and clock-change tests. In an app with staff or admin roles, each of their actions writes an audit row (who, when, what).
  - Accessibility: targets at least 24 × 24 px (WCAG 2.5.8), larger for main controls and the platform's own size on native apps; strong contrast; screen-reader labels.
  - Check each width the app supports.
  - Performance: name the screen's data reads, payload size and what loads lazily, per [efficiency](../../he/references/efficiency.md).
- Pick the first surface below that fits ([HE-REAL-APP-PREVIEW](../../he/references/requirements.md#he-real-app-preview)). Planning may build the proposal in an isolated checkout; production implementation still waits for Ready + authorization. No mandatory video or extra visual-testing platform.

| Surface                                           | Preview + baseline                                                                                                                                                                                                                                                                                                                   |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Existing — <actual route/screen + source owner>` | Required when the screen exists. Capture the unmodified app and render the proposal through that screen in an isolated checkout. Preserve its UI tree; assert route/state before capture. A reconstructed page is a Mock, not an actual-app capture.                                                                                 |
| `New — <new screen + source owner>`               | A new screen in an app that runs: render it in the app with repository components/tokens; the nearest existing flow is the baseline. Only an app with no prior UI may use `Before: N/A — <reason>`; label assumptions from the brief/assets.                                                                                         |
| `Mock — <actual design-system/component owners>`  | Only when the app cannot be built or rendered locally. Embed the change into the existing website reference, or make a lightweight HTML/image mock using its real design system; show decision-bearing states and label it a mock. Link an inspected baseline when available; otherwise `Before: N/A — <why the app cannot render>`. |
- Render + inspect = use existing browser/device tools; use [E2E](../../e2e/SKILL.md) for runtime visual inspection. For bitmap concepts/assets, use the available imagegen skill; HTML/CSS or existing vectors are sufficient otherwise. Inspect the rendered proposal at affected sizes/states and show it in the conversation. A path, unopened image or explanatory panel is not a shown workflow. Reuse inspected evidence while it still matches the proposal.
- Record = `Result` + `Evidence`, then `Surface`, `Before`, `Proposed`, `Capture`, `Review` in the existing plan. Proposed is a Markdown image. Capture names the actual rendering/capture method + observed result; Review names the inspected states/devices, comparison and direction. `Result: Passed` means the preview was rendered, inspected and shown; it does not record user approval. Before an approval handoff the direction may await the user's decision; Ready requires that decision settled within the task mode.
- Keep preview source isolated and artifacts in existing ignored/output storage. Link them without new receipts/hashes. Tracked non-Markdown files remain implementation inputs to the completion gate. Nonvisual work uses a concrete N/A reason; unavailable required proof remains blocked.
- User changes direction → update, inspect and show the matching mock/capture. For build verification, compare the actual app with the accepted reference and run the affected journey. A mock does not establish production fidelity or runtime success; recover the real before capture before implementation for PR evidence.

The gate validates declared fields, not image authenticity, design quality or whether the agent actually showed the proposal. Those require inspection; a Passed label cannot replace them.
