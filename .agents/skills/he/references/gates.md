| Parallelism             | Opt in only independent commands with distinct outputs; up to one runs per CPU, so account for child workers, memory + connections. Serial gates keep their order within a package; parallel gates run beside them, and serial gates of separate packages run at the same time, at most `max(2, CPUs / 4)` at once. Dependency setup runs first and performance suites run alone. A gate whose role is not read-only may write files: it runs before the gates of related packages (one folder inside the other, or a `depends_on` path) that follow it, and after readers inside its own folder. Two parallel gates other than scans never wait for each other. Parallel secret, vulnerability, security, workflow and shell scans start once those writers finish, beside serial suites. JavaScript tests clear `coverage/`, so no other gate in their folder runs beside them. A Fallow gate waits for the tests of the packages it depends on, whose coverage it may reuse. A command that writes outside its role, such as an iOS tests command that regenerates the parent app's code, belongs in its own generator gate. Setup runs a generated pytest gate with `pytest-xdist` and `-n auto`, and upgrades an older serial one on update. A suite that shares a database, port or fixed file across tests fails under it: isolate that state per worker, or keep the suite serial by setting `-n 0` in the gate command, which setup preserves.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

When no meaningful performance workload and justified budget exist, review the package's responsibilities and actual consumers before recording a nonblank `performance_exception` string in that package's gate group. Include the reason, inspected evidence and changes that require revisiting it. Package size or language alone is insufficient; missing tests or an inconvenient failing budget is not an exception. Remove only the unused template performance placeholder after review. Setup preserves the declaration and omitted check; every configured performance suite still runs with serial execution and native report validation. Unit tests, coverage and all other strict checks remain mandatory. The parser validates the declaration's shape, not the review's correctness.

CI adaptation starts at setup and is revisited whenever Hard Eng is adopted or updated or CI changes; it is not a second check runner or receipt store. Reuse native job dependencies and failure propagation; required checks must report for affected and unaffected changes. A deploy job can `needs:` a job that `uses: ./.github/workflows/hard-eng.yml` with the `base_sha` input; the called check reports as `<caller job> / hard-eng`, which `shipping.checks` must name. Push/PR execution requires a nonblank `--base`; use `github.event.pull_request.base.sha || github.event.before`, or the reusable workflow's `base_sha` input. Local and manual full runs may omit it. Review package impact before verification; an unavailable comparison ref or uncertain changed-file impact still selects full scope. Provision only the selected owners' tools, measure a cache before keeping it, and measure both critical-path time and runner minutes. Do not widen timeouts to conceal duplication. A build/performance/browser prerequisite remains required when its consumer moves jobs.

Measure setup, checks, waiting and deployment separately. Replace a runner polling another workflow with native `needs`/reusable-workflow ordering, then remove duplicate triggers. Install Hard Eng's tools without an Actions cache: on measured standard runners a restore took as long as the download, and saving a changed key cost more. Use the same package-manager store before dependency installation. Resolve each native workspace's locked dependencies once per job, before its consumers; remove duplicate workflow/wrapper installs only when the retained owner supplies the same dependencies and lifecycle scripts. Keep code generation once before its checks, retaining output-drift assertions; use Flutter's `--no-pub` only after the locked dependency gate succeeds. Remove repeated tests/scans only after comparing scope, tool versions, arguments and report thresholds. Dart Decimate's unfiltered strict `check` already includes boundary findings; its `--boundary-violations` option filters output and must not be added to the combined dead-code/duplicate gate.

Measure before and after each CI change: `python3 .hooks/hard-eng.py ci-usage [--repo owner/name] [--days 14]` reports billed minutes by workflow, event and job, whole-minute rounding, cancelled and failed minutes, jobs that never got a runner, and jobs run on both push and pull_request. Public repositories' standard runners are free, so optimise their wall-clock time instead. A push that lands one merged PR, or a release PR from the shipping base, reuses the passed required checks when it holds exactly the tree that passed; callers of the reusable workflow keep `contents: read` and `checks: read` so the lookup works, and any failed lookup runs the full check. Fix measured waste at its owner: fold jobs whose setup outweighs their work into a neighbour, replace polling with `needs`, cancel superseded runs with `concurrency`, bound each job with a measured `timeout-minutes`, keep macOS (10x) and Windows (2x) runners for platform code, and treat jobs that never got a runner as a runner-configuration fault.

CI audit: run `python3 .hooks/hard-eng.py ci-usage --runs 150`. Its slowest-jobs table splits each job into queue (created to started, which also holds time spent waiting for `needs` jobs), setup (set-up, checkout, install, cache and restore steps) and run; the Hard Eng job installs its tools inside the check step, so that part counts as run, and each gate's `elapsed` line in the job log shows where the check time goes. Then check, with seconds and the file line to change: queueing on default runners (`CI_RUNS_ON`), slow lint or type checks (gate `elapsed`), unsharded tests or small machines, test files that each start the whole app ([testing](testing.md)), slow setup (no tool cache by measured decision above; full clone, because a blobless clone with `persist-credentials: false` cannot fetch the history the secret scan reads; gate parallelism above), jobs that could run in parallel, PRs that run unaffected packages (affected selection above) and missing local checks before push. List options that cost money (new or larger runners) or run fewer tests separately for the user to decide.

`shipping.ci_seconds` bounds each named check's reported execution time. A three-second aggregate does not measure its upstream jobs: retain meaningful worker checks in the policy and measured native workflow/job timeouts. Report end-to-end CI elapsed time separately; do not claim a whole-pipeline budget from the aggregate's duration. Existing monoliths require a deliberate assertion-by-assertion migration before removing their product triggers; setup never deletes them automatically.

Basic mode (no supported manifest) has no packages: `packages` is empty and `shared` holds secrets-files, secrets-history, security (Semgrep `p/default`, excluding the installed `.agents` and `.hooks`) and, only when a lockfile OSV reads exists, vulnerabilities. Add project-owned checks as gates; CI installs only the bootstrap tools.

Shared roles: each is a gate in the `shared` list of `hard-eng.gates.json`, with `name`, `role`, `"parallel": true` and `command` as a list of words. Example: `{"name": "shellcheck", "role": "shell", "parallel": true, "command": ["shellcheck", "--", "scripts/build.sh"]}`; list every shell script of the project after `--`. `workflows` has the command `["actionlint", "-no-color"]`. `ci-security` has `["zizmor", "--strict-collection", "--persona=auditor", "--format=plain", "."]`. `deployment` has `["trivy", "config", "--exit-code", "1", "--format", "json", "."]` and `"report": {"type": "trivy", "path": "coverage/trivy.json", "stdout": true}`, so Hard Eng saves Trivy's output to that file. Copy `secrets-files`, `secrets-history` and every other shared role from the `shared` list of the language template below.

`freshness` fails when a direct or dev dependency is older than its newest stable release that is at least 2 days old (Bun, Dart/Flutter, uv, Poetry; not Swift; Dart and Poetry stop at the newest version their solver can resolve; Bun skips peer ranges; a Poetry entry that Hard Eng cannot raise (git, path, url, `optional`, `develop` or no plain version) gets a note and passes). Upgrade in a separate PR before other work ([baseline repair](plan-checks.md#baseline-repair)). To skip a broken release, add `{package, version, reason, until}` to that gate's `holds`: `version` is the skipped release, `until` a `YYYY-MM-DD` date at most 14 days away; after it, the gate fails again. An "Update Hard Eng" PR skips the gate.

Setup and `check` leave a JavaScript package root file named `<tool>.config.<js|mjs|cjs|ts|mts|cts>` out of the `sources` list when `<tool>` is a name in `TOOL_CONFIGS` of `.hooks/coverage_sources.py`, so it needs no coverage. `<tool>.<part>.config.<ext>` and `<tool>.config.<part>.<ext>` stay out too. Never add a name to `TOOL_CONFIGS`; list the file. Every other root `.config.` file, such as `auth.config.ts`, is project code and needs listing. A file already named in `sources` keeps its coverage check.

Use existing [Python](../templates/hard-eng.python.json), [JavaScript](../templates/hard-eng.javascript.json), [Dart/Flutter](../templates/hard-eng.dart.json) or [Swift](../templates/hard-eng.swift.json) templates when adapting a new package. A check with no report, in a role its package language requires, must hold that role's tool words, next to each other, in its command, for example `ruff check`, `biome ci`, `dart analyze`, `swift format lint` or `actionlint`. `ROLE_TOOLS` in `.hooks/tool_setup.py` lists the words for every role; they are the words the template command runs. `check` refuses a command without those words. A `uvx` prefix, an inline `sh -c` script and, in a JavaScript package, a Bun script all pass; a script file that hides the words is refused. Only the words are checked, so never hide the tool's failure (no `|| true`, no exit-zero flag). A project's own extra check, such as another linter, takes a role name of its own. A tests or performance gate refuses the flags that run only part of its suite (name, tag, changed-only, last-failed, shard, project and path-ignore flags); `reject_test_filters` in `.hooks/gate_runner.py` owns the list. To split a pytest tests gate over N CI jobs, add the field `"shards": N` (2 to 16) to that gate in `hard-eng.gates.json`; only one gate of a package can hold it. It is a field of the gate, not a shard flag in the command: the command must run pytest directly. A `shards` gate refuses a test path, `-c`, `--config-file`, `--cov-config`, `--cov-precision` or `-o addopts` in the command or pytest `addopts`; shard jobs also refuse `PYTEST_ADDOPTS` or `COVERAGE_RCFILE` if set. Each refusal prints the fix. When the field is on the base branch, rerun setup: the `hard-eng/update` branch then holds a `hard-eng-checks` job, N `hard-eng-tests` jobs and the required `hard-eng` job in the workflow that setup generated, and the step that setup prints opens its PR. A customised workflow gets a note and stays as it is. Each shard job keeps the timeout of the one job. The `hard-eng` job merges the shard reports, applies Hard Eng's coverage minimum and the project's own to the merged total, and applies the test rules. A local `check` still runs the whole suite. To go back to one job, remove the field and rerun setup. Setup adds a Swift group per Flutter `ios/` or `macos/` folder with an Xcode project and Swift beyond Flutter's unchanged starter files (compared by text with Flutter's templates), and removes the group when only starter files remain; unchanged starter files are not production files; its tests need macOS, so CI runs only the Swift groups in a `hard-eng-apple` job when `impact` prints `apple=true`, and every other group on the Linux runner; `check --only-language swift` and `--skip-language swift` select the two halves. Measured on a fresh Flutter app on a loaded Mac: iOS `tests` 231 s on the first run and 45-67 s after, macOS `tests` 18 s, every other Swift gate under 5 s; set `shipping.ci_seconds` from your own macOS run, which also downloads Flutter and the iOS engine. Do not copy a template over project-specific contracts.

## Adopting existing checks

At setup, list the project's existing checks (pre-push/pre-commit hook commands, lefthook, pre-commit or husky configs, CI check jobs) beside Hard Eng's gates and show the user a comparison table. A project pre-push hook is kept and runs first; Hard Eng's checks run only if it passes.

- Hard Eng's gate does the same or better → use Hard Eng's.
- Project check does something Hard Eng lacks → keep it as a gate in `hard-eng.gates.json`, so the single pre-push runs everything, and file a gap issue: `python3 .hooks/hard-eng.py gap-issue "<missing check, generic>"`. File without asking. Never include project names, code, paths or data; the command refuses paths, file names, URLs, emails and long text.
- Unsure → keep both.

Existing code that fails Hard Eng's gates at install: run `python3 .hooks/hard-eng.py adopt` before the install reaches the default branch, and commit `hard-eng.debt.json` with it ([HE-DEBT-SHRINK-ONLY](requirements.md#he-debt-shrink-only)). Gates that adopt refuses follow [baseline repair](plan-checks.md#baseline-repair).

Remove nothing project-owned until the user approves the table. After approval, a fully absorbed original hook can be dropped from the chain by deleting its `.project` copy and rerunning setup.
