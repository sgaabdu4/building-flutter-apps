# Bulk + async + performance

Apply only to the changed flow, unless the user asks for a wider scan. Derive limits from its actual service/behavior contract; unknown limits remain unverified.

| Flow            | Implementation + meaningful assertion                                                                                                                                                                                                                                        |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Batches         | Reuse native batching/pagination/streams. Exercise empty, boundary + final partial inputs; assert exact records/order, no loss/duplication + expected calls. Account for payload limits and retries, not only item count.                                                    |
| Fan-out / queue | Bound active + pending work; define overload behavior. Hold workers at a controlled boundary, prove both bounds, then release and verify completion, errors + relevant cancellation/timeout cleanup. A semaphore around eagerly created tasks does not bound pending memory. |
| Repeated I/O    | Assert required query/request counts across representative input sizes, cache states + partial failures. Retries must not duplicate effects or amplify overload.                                                                                                             |
| Scaling         | Name input dimensions + expected time/space growth; inspect repeated scans, copies, sorts + I/O. Assert independently justified operation bounds where feasible; include skewed inputs when relevant.                                                                        |

Use controlled inputs, fake clocks or synchronization instead of sleep-based comparisons. Native pattern lints and timing samples do not prove general Big-O.

Async does not make CPU work parallel; unbounded gathers can worsen resource use.

Independent work: use the bounded-concurrency helper. Dart and Swift use `mapWithConcurrency`; JavaScript and TypeScript use `mapLimit`; Python uses `map_with_concurrency`. Reuse the project's helper and keep its concurrency bound explicit. A raw loop that awaits a join still needs the helper; step width, chunk names and join layout do not exempt it.

C1 only reads a literal 1 at the call. Write ordered work with inOrder. Only the second positional argument is the supported positional bound; an explicit named width takes precedence. Named bounds and inline JavaScript options require a literal one. Inline options must have no top-level spread or duplicate bound key. Identifier widths, computed bounds, computed property keys and options variables remain outside guaranteed coverage.

Each loop is judged on its own, including loops inside async context managers. A helper body or an outer loop's early exit, sleep or condition update does not exempt a nested loop. Python `async with` waits on context entry and exit even without an explicit body await; task groups from asyncio and anyio also join their tasks. A raw loop containing these waits needs a named helper.

Ordered work: use `inOrder` or `inOrderSteps` with a reason; Python uses `in_order` or `in_order_steps`. Pass a static `reason` string with at least 20 characters and more than one word. Literals, constants and literal concatenations are accepted. Dart and Swift use `reason: "..."`; JavaScript uses `{ reason: "..." }`; Python uses `reason="..."`. Write the reason inline at the helper call; options variables are not supported. State the real order constraint. Keep the helper's loop plain; never hide the order with recursion, streams or comments. When TypeScript or Biome flags `reason` as unused in the project's own `inOrder` or `inOrderSteps` definition, make `void reason;` its first statement (`void _reason;` when it destructures `{ reason: _reason }`).

## Hot paths + data layout

[HE-HOT-PATH](requirements.md#he-hot-path) fails each case below that a pattern can find, in old code too; `python3 .hooks/hard-eng.py hot-paths` lists them. Rewrite each finding as the table says; never hide one by moving the same work where the pattern cannot see it. For a requested scan ("deep scan hot paths", "find every place we ..."), run `python3 .hooks/hard-eng.py hot-paths`, then read the request handlers, jobs and loops that patterns cannot judge. Fix each confirmed case at its owner, one per commit.

| Case             | Do                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Sequential async | Use the bounded-concurrency helper above for independent work. Keep a sequence only when a call needs the previous result, the order is part of the contract, or a rate limit requires it. The rules accept: calls on one session, connection, transaction, cursor, socket, page or dialog; a loop over an async stream; a worker loop; a loop that stops early, updates a value its condition reads, or sleeps between calls.                                               |
| Whole rows       | Select only the columns the caller reads: SQL column lists, Prisma `select`/`omit`, Drizzle `columns`, Django `.only()`/`.values()`, SQLAlchemy `load_only` or column selects, Appwrite `Query.select`. To change a row, write only its changed columns (`.filter(...).update(...)`, `save(update_fields=...)` after `.only()`, an `UPDATE` statement).                                                                                                                      |
| URL parsing      | Parse once at the boundary and pass the parsed object or the part needed. Compare strings when only a prefix or origin check is needed.                                                                                                                                                                                                                                                                                                                                      |
| Regex            | Build each constant regex once at module level (top-level or `static` in Dart and Swift). A JavaScript `g` or `y` regex keeps `lastIndex`, so build it where it is used.                                                                                                                                                                                                                                                                                                     |
| JSON columns     | Store each key as a typed column (indexed when queried) and each list as a child table. Keep a large schema-free document in object storage and its key in a column. Migrate in deployable steps: add the column, backfill, switch reads, remove the JSON column.                                                                                                                                                                                                            |
| Caches           | Do not add a cache; find why the work is slow and fix that (query, index, data layout, algorithm). When asked to remove existing caches, redesign the slow path and measure before and after per Optimisation, because removal can raise load on a shared service. HTTP cache headers and CDN rules are delivery contracts.                                                                                                                                                  |
| Data layout      | In hot loops over many records: arrays indexed by dense integer IDs instead of hash maps; indexes instead of object references; a structure of arrays when a loop reads few fields of many records (typed arrays, NumPy, `typed_data`, `ContiguousArray`); bitsets instead of boolean arrays; hot flags packed into spare index bits and fixed-capacity inline storage (Swift `InlineArray`) only when measured. Python, JavaScript and Dart cannot choose stack allocation. |

## Optimisation

Only when the requested outcome is a measured improvement (time, memory, size, cost):

1. Reproduce the real workload. The plan names the metric, target, measurement command and correctness constraints.
2. Show the measurement detects a known change, then freeze the workload, command and configuration for the comparison.
3. Record revision, configuration and repeated samples on both sides, enough that the difference exceeds run-to-run spread. Never run competing measurements on the same constrained CPU, disk or network.
4. One hypothesis per change: measure before and after, run the existing gates, and keep only demonstrated improvements or equally fast simplifications. Revert rejected task-owned changes only.
5. Record baseline, samples and decisions in the plan's Baseline/Verification. Stop at the authorised target or budget, or when further work is unjustified; never weaken a check or shrink the workload to meet a target.

Diagnose surprises with [troubleshooting](../../research/references/troubleshooting.md); prove affected journeys per [testing](testing.md).
